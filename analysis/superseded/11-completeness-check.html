Elan1 Govern · front end · read-only check

Completeness check — after the build

28 October 2026, night. Nothing was built or changed for this check. It covers the console, the receipt verifier, the developer portal, the counterparty, regulator and partner portals, the status, legal, fingerprint, maintenance and offline pages, and every demo sign-in, at L1, L2, L3 and Sovereign. The public site is not included: it is already built.

How it was checked.
  • Code reviews. Five reviewers each read one area against the platform plan and the digests of the Information Memorandum, Technology Memorandum, Architecture Atlas and financial model. The five areas were: Work and access; Records; Agents and Sovereign; Assurance and billing; and the developer portal with the end-to-end journeys. Each finding comes with a file and line. I re-checked the most important findings in the code myself.
  • Sign-in check. Every demo account was tried in the running app with its published password.
  • Link checks.
    • Static: every link target in the code was matched against the routes, including tab values and anchors.
    • Live: every link was followed in the running app at each level. The live crawl was run earlier tonight on the same code.
Not counted: the decisions in 08-conflict-decisions.md, the defaults listed in §4 of 10-build-report, items the memorandum marks LATER, the public site and backend internals.

All the screens exist, all the links resolve, and all the demo sign-ins work. The 45 findings are mostly details inside screens that already exist:

  • a level gate or a line of copy that disagrees with the 28 Oct decisions;
  • a role permission that differs from the Technology Memorandum's role table;
  • a flow that stops one step short.

Five matter most:

  • Emergency stop confirmation. Typing "stop" in lowercase leaves the button disabled, with no message.
  • Packs at L1. Packs can't be installed from the Coverage page, and no agent can be admitted to a pack.
  • Pack checks on live calls. An installed pack's checks never decide a live call.
  • Sovereign egress. Approval links and single sign-on can still reach outside services, despite deny-all egress.
  • Auditor writes. An auditor can write receipts to a client's chain.

4. Known and accepted

  • The pilot in the demo organisations. The pilot invoice line and the Today tile appear only in organisations created by sign-up. This is already noted in 10-build-report.
  • Seeded demo events. They carry the time the seed ran, not a back-dated time, so the chain's timestamps keep running forward.
  • Single-authority batches. The verifier handles a batch with only one timestamp authority ("degraded") in code. But every seeded batch has two, so it can't be shown in the demo.

5. What this check could not cover

  • Reviews. The five code reviews read the code; they did not click through the app. The live crawl covers rendering, links and script errors, but not every button's result.
  • Single-use links. Single-use approval and portal links were not opened, because opening one uses it up or records a view.
  • Devices. Phone layouts at 360 px and installing the app on a real phone were not tested.
  • Read in part. Some large screens were checked by targeted search rather than read line by line: the counterparty drawers, disclosure, bundles and the later part of the close-out page.
