Are all the reported items really fixed?

28 October 2026, late night. This check was read-only; nothing was built or changed. It covers every Broken, Missing and Partial item listed in 11-completeness-check (45 items) and 13-completeness-check (42 items), at L1, L2, L3 and Sovereign. The public site is not included.

Short answer: not completely.
  • 82 of the 87 items are fully fixed in the code as it stands now.
  • 5 are only partly fixed: their main problem is gone, but a piece remains (§3).
  • None is still unfixed.
  • The fixes caused 13 smaller side effects (§4). Most are wording and documentation; one (onboarding at L3 and Sovereign) affects a real flow.

For each item they read the original finding and traced the actual code path, from screen to API to mock, not just the wording. Each item got a verdict of Fixed, Partly fixed or Not fixed, with the file and line as evidence.
  • My own re-checks. I re-checked every Partly verdict and the main side effects myself.
  • Earlier evidence. These results build on the tests already run tonight: the type-check and build pass, the 64 Seal v6 test vectors pass, bundles verify at three levels, and the live crawl of all four levels found 0 problems.

2. Why each new check found more items

Each check was asked an open question: is anything missing or partial anywhere? It was not asked whether last time's items were fixed. That is why every round produced a new list, even though most earlier items were in fact fixed.

RoundWhat it foundHow many earlier items were really still open
First check (report 11)45 items—
Second check (report 13)42 items34 of the 45 were confirmed fully fixed. 11 had a remaining piece. The other 31 items were new.
This verification (report 15)Only the 87 listed items, plus side effects seen while checking82 of 87 are fully fixed; 5 have a remaining piece.

The new items came from three sources:

  • Deeper reading. Each round's reviewers start fresh and read further into areas the last round only skimmed: the developer docs, cookie and legal text, billing edge cases.
  • Side effects of large fixes. Each fix round changed about 100 files. A change in one place can leave a neighbouring screen out of step. For example, the key-rotation fix left Proof › Keys showing an approved rotation as still waiting.
  • A long tail. The platform is checked against several hundred pages of documents across four levels, so an open-ended hunt keeps finding something.

The severity has fallen sharply:

  • The first round found things like a broken emergency-stop confirmation and packs that could not be installed.
  • This round's remaining items are mostly wording, documentation and edge cases.

The way to reach "done" is a closed list: fix the items below, then verify only those, as this report does, rather than running another open-ended hunt.

6. What it would take to close this out

  • The 5 partly fixed items and the 13 side effects are all small and local, except S1, which is about onboarding. Together they are a closed list of 17 changes (two of the partly fixed items share a cause); one agent working through the list is enough.
  • 11 #31 needs your ruling. Keep today's member file names with the documented mapping, or rename them to the specification's names. Renaming means bundles exported before the change no longer match.
  • After those fixes, verify only that closed list, as this report does. Another open-ended "check everything" will always find something new in a platform of this size.

7. Limits of this check

  • Code, not clicks. This round traced code; it didn't click through the app. The live crawl and the scripted checks run earlier tonight cover rendering, links, the verifier and the main flows.
  • Pack checks. No pack admissions are seeded, so the pack-check paths were traced in code and scripts, not seen on a real demo receipt.
